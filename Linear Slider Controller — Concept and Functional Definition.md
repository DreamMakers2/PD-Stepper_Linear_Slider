# Linear Slider Controller — Concept and Functional Definition

The system is a Wi-Fi-connected controller for a belt-driven linear slider using the PD-Stepper hardware, a NEMA 17 motor, a GT2 20-tooth pulley, and the onboard AS5600 magnetic encoder. The firmware should run directly on the PD-Stepper ESP32 and expose a simple network API. No embedded website or user interface is required. All motion control, homing, safety monitoring, driver configuration, and fault handling must remain local to the controller so that loss of Wi-Fi or an interrupted API request cannot leave the mechanism moving uncontrolled.

The controller should preserve the useful functionality available in the original PD-Stepper web-server firmware. This includes motor enable and disable, velocity control, position movement, safe PD supply-voltage selection limited to 5 V, 9 V, or 12 V, microstep configuration, motor-current configuration, StallGuard threshold, standstill mode, and access to operating data such as power-good state, measured VBUS voltage, AS5600 encoder position, TMC2209 driver status, StallGuard value, and DIAG state. These functions should be exposed through a compact JSON-based API rather than through the original webpage. Additional state should include the current motion mode, homing status, calibrated travel limits, position in millimetres, active fault, and other information needed by an external controller. A read-only `/api/help` JSON manifest should describe the routes, fields, limits, fixed homing behavior, buttons, and operating constraints without adding a webpage.

The normal mechanical configuration is a 1.8° NEMA 17 motor driving a GT2 belt through a 20-tooth pulley. One motor revolution therefore produces approximately 40 mm of linear travel. The usable slider range is approximately 470 mm. Position should internally be handled in physical units where practical, while encoder counts and motor steps remain available as diagnostic values.

The controller should support a single high-level command to home the complete slider. Homing establishes both physical ends of travel without mechanical limit switches. The operation first moves toward one end until the TMC2209 DIAG signal indicates a StallGuard event. Motion must stop immediately when this occurs. The carriage then backs away from the stop by approximately 5 mm. The controller subsequently moves toward the opposite end, again stopping immediately on DIAG, records that location as the second limit, backs away by approximately 5 mm, and moves to the calibrated midpoint. The two detected endpoints define the valid travel range. One endpoint becomes position zero and the measured distance between them becomes the calibrated maximum position. Once this process completes successfully, the controller reports itself as homed and uses the calibrated range as soft travel limits during normal operation.

Homing should use a 12 V PD supply, 800 mA RMS motor current, 4× microstepping, 1000 microsteps/s homing speed, 1500 microsteps/s² acceleration, StallGuard threshold 100, TCOOLTHRS 210, DIAG on GPIO16, and StealthChop enabled. Before motion, the enabled driver should remain at the full homing run-current scale for approximately 150 ms so StealthChop standstill auto-tuning can complete at 12 V. It then uses deterministic NORMAL standstill with 50% hold; this is an implementation decision that freezes the repository's previous/default behavior because the persisted setting used by the historical hardware test was not recorded. The complete cycle remains at 4× and the fixed driver settings through both endpoints, both backoffs, and the automatic midpoint move. The midpoint uses 40 mm/s and 75 mm/s². Runtime settings are restored only after centering succeeds. Higher PD voltages must not be selectable. These fixed values were selected from captured free-running and endpoint StallGuard measurements on the 12 V mechanism; the general runtime settings do not override them, and API attempts to modify the homing object are rejected as `INVALID_CONFIG`.

A StallGuard event must never be the only protection against continued motion into a mechanical stop. Every homing seek must terminate if 500 mm of commanded travel is reached or 15 seconds elapse without a valid stall event; each 5 mm backoff has a 2-second limit. Any limit violation means homing has failed. The motor must stop, the driver should be disabled, the homed state must remain false, and the controller must report a clear `HOME_FAILED` fault. There must be no behaviour in which the motor continues driving or repeatedly attempts to push against the stop after a failed detection.

DIAG and power-good emergency events must drive `ENN` high and force-stop FastAccelStepper immediately. Because STEP generation may stop before its queued count represents the final physical position, the controller must explicitly resynchronize FastAccelStepper from the AS5600 afterward. A homing DIAG endpoint may be accepted only after one clean TMC UART/status check rejects communication failure, overtemperature, and obvious short-circuit faults.

The AS5600 encoder provides a separate last-resort hard-stop protection mechanism. This protection compares commanded motor movement with actual shaft movement over a rolling window of approximately 125 ms. A probable mechanical obstruction exists when commanded movement exceeds observed movement by approximately 164 AS5600 counts within one window, equivalent to about 14.4° of motor rotation. Error must not accumulate across windows. This comparison should be expressed primarily in encoder counts or physical motor angle rather than a fixed number of microsteps, because the equivalent microstep count changes when the selected microstep setting changes.

Once a rolling window meets the hard-stop condition, STEP generation must stop immediately, the motor driver must be disabled, and a latched hard-stop fault must be reported. The window rejects shorter transient oscillations, belt elasticity, and reversal effects without adding a second delay after the movement mismatch is established. Further movement should require an explicit fault reset or a new controlled homing procedure.

Normal motion must respect the calibrated endpoints and should stop before reaching the physical hard stops. Physical contact with the ends is therefore expected mainly during controlled homing or as the result of an abnormal condition. Commands that request movement outside the calibrated range should be rejected or clamped to the valid range rather than executed directly.

Normal motion defaults to 50 mm/s and 75 mm/s², with allowed software ceilings of 150 mm/s and 300 mm/s². These normal defaults are persistent and configurable. Runtime NORMAL uses 30% hold current, subject to driver-register quantization. Fresh configuration defaults to 32× microstepping and freewheeling; both remain persistent and configurable. Existing stored values are preserved during upgrades rather than silently migrated.

The unwrapped AS5600 calibration is independent of microstep resolution. An idle runtime microstep change must capture the encoder, disable the driver, apply and verify the new resolution, recalculate pulses per millimetre, capture again, and rebase FastAccelStepper without clearing the endpoints. Public 1× maps to the TMC driver's full-step setting. Direction or encoder-polarity changes still invalidate calibration.

While homed and stationary, encoder-derived millimetres are authoritative. Manual movement in freewheel mode updates the physical, commanded, and FastAccelStepper coordinates. Before every powered move from FREEWHEELING, the controller captures and rebases, re-engages the rotor using a non-freewheel hold, waits only for bounded encoder stability rather than assuming a generic enable delay, then captures and rebases again before restoring FREEWHEELING and queueing the requested movement. A small alignment movement may occur and must not be claimed impossible. This behavior assumes continuous controller power, valid encoder readings, intact motor-to-carriage coupling, and manual placement inside calibrated limits; a motor-shaft encoder cannot detect belt or pulley slip.

The fixed homing profile still uses `invert_direction` and `invert_encoder` as installation-specific logical-orientation transforms. Changing either transform invalidates the calibrated limits and requires a new homing cycle.

All movement should be managed by one internal motion-control state machine. Network requests should request high-level actions such as move, velocity, stop, home, enable, disable, or configuration changes; they should never directly control STEP, DIR, or TMC2209 registers while motion is active. Safety events such as DIAG, encoder hard-stop detection, power loss, homing timeout, or travel-limit violation must always have priority over API commands.

The three active-low side buttons are local controls. GPIO35 holds a jog toward calibrated MIN and GPIO37 holds a jog toward calibrated MAX; both require successful homing and stop/resynchronize on release. Pressing both inhibits jogging until both are released. Holding GPIO36 for at least one second and releasing requests homing. If GPIO36 is pressed during any motion, an interrupt-level stop must immediately disable ENN and force-stop STEP generation; main-loop cleanup cancels queued work and clears calibration so re-homing is mandatory. The stop remains latched until a debounced release and takes precedence over DIAG endpoint processing. It is a software safety stop, not a hardware e-stop.

The firmware-controllable LEDs on GPIO10 and GPIO12 should be driven low before the startup delay and remain off during operation.

The controller should distinguish clearly between normal operating states and faults. Useful states include disabled, idle, moving, homing toward minimum, homing toward maximum, backing off, and faulted. Fault information should identify homing failure, encoder hard stop or read failure, dedicated TMC UART communication failure (`TMC_COMM`), TMC electrical/thermal failure, power-good loss, travel-limit violation, and an unexpected DIAG stall. Faults are latched; reset leaves the driver disabled and calibration invalid. A stop command should always be available and should take effect immediately regardless of the current normal motion command.

An optional session-maintenance firmware-upload route may be compiled only when a token is supplied from the ignored local Wi-Fi configuration. It is not a normal motion API: unauthorized requests must be rejected, uploads must be refused while the driver is enabled or the controller is moving, and successful updates use the existing OTA application slot without changing the bootloader or partition layout.

The intended result is a self-contained linear-motion controller that can be integrated into another application through Wi-Fi without depending on a browser interface. The external system sends simple commands and reads state, while the PD-Stepper itself remains responsible for precise motor operation, endpoint calibration, travel enforcement, StallGuard handling, encoder supervision, and safe shutdown whenever expected motion does not occur.
