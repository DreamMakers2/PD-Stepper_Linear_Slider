# Linear Slider Controller — Concept and Functional Definition

The system is a Wi-Fi-connected controller for a belt-driven linear slider using the PD-Stepper hardware, a NEMA 17 motor, a GT2 20-tooth pulley, and the onboard AS5600 magnetic encoder. The firmware should run directly on the PD-Stepper ESP32 and expose a simple network API. No embedded website or user interface is required. All motion control, homing, safety monitoring, driver configuration, and fault handling must remain local to the controller so that loss of Wi-Fi or an interrupted API request cannot leave the mechanism moving uncontrolled.

The controller should preserve the useful functionality available in the original PD-Stepper web-server firmware. This includes motor enable and disable, velocity control, position movement, safe PD supply-voltage selection limited to 5 V, 9 V, or 12 V, microstep configuration, motor-current configuration, StallGuard threshold, standstill mode, and access to operating data such as power-good state, measured VBUS voltage, AS5600 encoder position, TMC2209 driver status, StallGuard value, and DIAG state. These functions should be exposed through a compact JSON-based API rather than through the original webpage. Additional state should include the current motion mode, homing status, calibrated travel limits, position in millimetres, active fault, and other information needed by an external controller.

The normal mechanical configuration is a 1.8° NEMA 17 motor driving a GT2 belt through a 20-tooth pulley. One motor revolution therefore produces approximately 40 mm of linear travel. The usable slider range is approximately 470 mm. Position should internally be handled in physical units where practical, while encoder counts and motor steps remain available as diagnostic values.

The controller should support a single high-level command to home the complete slider. Homing establishes both physical ends of travel without mechanical limit switches. The operation first moves toward one end until the TMC2209 DIAG signal indicates a StallGuard event. Motion must stop immediately when this occurs. The carriage then backs away from the stop by approximately 5 mm. The controller subsequently moves toward the opposite end, again stopping immediately on DIAG, records that location as the second limit, and backs away by approximately 5 mm. The two detected endpoints define the valid travel range. One endpoint becomes position zero and the measured distance between them becomes the calibrated maximum position. Once this process completes successfully, the controller reports itself as homed and uses the calibrated range as soft travel limits during normal operation.

Homing should use a 12 V PD supply, 800 mA RMS motor current, 4× microstepping, 800 microsteps/s homing speed, 1500 microsteps/s² acceleration, StallGuard threshold 20, TCOOLTHRS 400, DIAG on GPIO16, and StealthChop enabled. Higher PD voltages must not be selectable. With the specified pulley and motor this corresponds to approximately 40 mm/s homing speed.

A StallGuard event must never be the only protection against continued motion into a mechanical stop. Every homing movement must also have independent distance and time limits. A homing leg must terminate if approximately 500 mm of commanded travel is reached or if approximately 15–20 seconds elapse without a valid stall event. Either condition means homing has failed. The motor must stop, the driver should be disabled, the homed state must remain false, and the controller must report a clear `HOME_FAILED` fault. There must be no behaviour in which the motor continues driving or repeatedly attempts to push against the stop after a failed detection.

The AS5600 encoder provides a separate last-resort hard-stop protection mechanism. This protection compares commanded motor movement with actual shaft movement. A probable mechanical obstruction exists when commanded position continues advancing while the encoder shows little corresponding net movement. The detection threshold should represent approximately eight full motor steps of accumulated disagreement, equivalent to about 14.4° of motor rotation or approximately 164 AS5600 counts. This comparison should be expressed primarily in encoder counts or physical motor angle rather than a fixed number of microsteps, because the equivalent microstep count changes when the selected microstep setting changes.

The hard-stop condition should persist for approximately 100–150 ms before being accepted as a fault. This persistence allows short transient oscillations, belt elasticity, reversal effects, and brief StallGuard buzzing without unnecessary trips. Once the sustained encoder-error condition is confirmed, STEP generation must stop immediately, the motor driver must be disabled, and a latched hard-stop fault must be reported. Further movement should require an explicit fault reset or a new controlled homing procedure.

Normal motion must respect the calibrated endpoints and should stop before reaching the physical hard stops. Physical contact with the ends is therefore expected mainly during controlled homing or as the result of an abnormal condition. Commands that request movement outside the calibrated range should be rejected or clamped to the valid range rather than executed directly.

All movement should be managed by one internal motion-control state machine. Network requests should request high-level actions such as move, velocity, stop, home, enable, disable, or configuration changes; they should never directly control STEP, DIR, or TMC2209 registers while motion is active. Safety events such as DIAG, encoder hard-stop detection, power loss, homing timeout, or travel-limit violation must always have priority over API commands.

The controller should distinguish clearly between normal operating states and faults. Useful states include disabled, idle, moving, homing toward minimum, homing toward maximum, backing off, and faulted. Fault information should identify at least homing timeout, homing distance exceeded, encoder hard stop, TMC driver fault, and loss of valid motor power. A stop command should always be available and should take effect immediately regardless of the current normal motion command.

The intended result is a self-contained linear-motion controller that can be integrated into another application through Wi-Fi without depending on a browser interface. The external system sends simple commands and reads state, while the PD-Stepper itself remains responsible for precise motor operation, endpoint calibration, travel enforcement, StallGuard handling, encoder supervision, and safe shutdown whenever expected motion does not occur.
